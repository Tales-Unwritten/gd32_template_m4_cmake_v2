# AI 练习任务生成标准（Practice Task Authoring Spec）

> **用途**：规范 AI（或本人）生成新练习作业的方式，使每份作业简洁、可验收、可复用。
> 现有作业与方案库见 [`practice_tasks.md`](practice_tasks.md)。

---

## 1. 目的

把"出练习题"变成**可复制、可定制**的事：给出少量输入（需求、器件、目标能力、难度），
即产出一份结构统一、边界清晰、可独立验收的作业。目标始终是——
**让学习者熟练把一个需求实现出来**，而非"背诵某个 API"。

---

## 2. 角色与分工

| 角色 | 职责 |
|------|------|
| AI（出题方） | 定需求、定白名单、定验收；审核打分；指导修改 |
| 学习者 | 在**白名单函数 + 允许文件**范围内自行设计并实现；交付实测结果 |

**铁律**：出题方**只出题、不代写实现代码**。白名单外 API 需先申请并说明理由。

---

## 3. 输入（生成一份新作业所需）

| 输入项 | 说明 | 缺省 |
|--------|------|------|
| 需求 | 一句话说要交付什么 | 必填 |
| 目标器件 / 数据结构 | INA228 / AT24C02 / W25Q128 / LED / 按键 / CAN / 缓冲区 / 状态机… | 必填 |
| 目标能力 | 想练的 FreeRTOS 或纯代码能力 | 选填 |
| 难度 | L1 入门 / L2 进阶 / L3 综合 | 默认 L1 |
| 通道 / 协议 | 默认 `debug_uart` + ASCII 指令 | 默认值 |

---

## 4. 作业文档模板（强制 · 三段式）

```markdown
### 作业 <编号> —「<标题>」

**功能**
<交付什么；指令类按器件能力铺满，用表格列出 指令 → 回复>

**限定**
- 只能改：<项目相对路径> …
- 只能用：<函数白名单，精确到函数名>
- 技术：<必须用到的机制，如 队列 / 互斥 / 状态机>

**验收**
1. <可复现的通过条件，含边界/异常>
2. …
```

- **只有这三段**。不写"业务背景""常见坑"——理由与坑改由对话中口头说明。
- 指令/回复格式必须精确（含 `\r\n`）。
- 编号：主线用 `A0/A1…`；外设/产品类 `B#`；纯代码类 `C#`。

---

## 5. 硬性规则

### MUST

1. **需求实用为主**：像真实工单；**指令类必须按器件能力铺满**，不能只定义一个功能。
2. **一个作业 = 一个需求**；知识点/技术是手段，不是目的。
3. **三段式齐全**：功能、限定、验收缺一不可。
4. **限定精确**：白名单精确到函数名；单独列出"技术"；圈定允许改动的文件。
5. **验收可复现**：含正常路径 + 边界/异常 + 稳定性（连续 N 次/运行 M 分钟）。
6. **真实存在**：器件、引脚、API 必须在项目中真实存在（见第 7 节核实流程）。
7. **难度递进**：L1 只涉及 1~2 个新能力；L3 可组合多个。
8. **遵守分层**：SDK 只在 `interface/src/`；GPIO 只经 `io_ctrl`；命名小写+下划线；LF。

### MUST NOT

1. 不得在题目里给出完整实现代码（可给函数名、数据字段、格式要求）。
2. 不得引用不存在或冲突的 API（如 `suart`/`debug_uart` 同引脚不能同用）。
3. 不得把"知识点演示"当作业（如"用队列做个生产者消费者"没有需求外壳）。
4. 不得放宽到"任意实现"：必须圈定文件与可调用函数。
5. 不得要求修改 `Firmware/`（SDK 只读）。

---

## 6. 验收标准规则

- 每条能**独立判定通过/失败**，不依赖主观描述。
- 至少覆盖：**正常路径**、**边界/非法路径**、**稳定性**。
- 优先给**上位机可观测**的结果（串口原始报文），便于截图佐证。
- 标注自测手段（如 `uxTaskGetStackHighWaterMark` 看栈余量）。

---

## 7. 出题前置流程（必须核实 API 存在）

1. 读取相关文件与头文件（`interface/`、`device/`、`protocol/`、`user/`）。
2. 确认目标 API 的**确切名称、参数、返回值**。
3. 确认硬件资源未被占用 / 无冲突（引脚、总线、EXTI 线、外设）。
4. 确认 FreeRTOS 侧所需能力已在 `FreeRTOSConfig.h` 开启。
5. 确认允许改动的文件位置符合分层与命名规则。
6. 再输出「功能 / 限定 / 验收」。

---

## 8. 评分维度（审核用）

| 维度 | 关注点 |
|------|--------|
| 需求符合度 | 各功能点逐条满足；边界行为与说明一致 |
| 分层 / 规范 | SDK 边界、GPIO 走 `io_ctrl`、命名、LF |
| 并发安全 | `volatile`、互斥、撕裂读、`FromISR` |
| 实时性 | 无忙等、无阻塞采样、无栈溢、ISR 极简 |
| 容错 | 非法输入、超时、队列满、拔线、复位 |
| 交付 | changelog 更新、说明清晰度 |

---

## 9. 难度分级

| 级别 | 新能力数量 | 典型 |
|------|-----------|------|
| L1 入门 | 1~2 | 任务创建、延时、简单轮询 |
| L2 进阶 | 2~3 | 队列、互斥、`volatile`、状态机 |
| L3 综合 | ≥3 或跨模块 | 事件组 + 定时器 + 看门狗组合、多任务协同 |

---

## 10. 交互协议（AI ↔ 学习者）

```
学习者给输入（需求/器件/能力/难度）
  → AI 复述理解并确认（含糊先澄清）
  → AI 核实项目内 API（第 7 节）
  → AI 输出三段式作业
  → 学习者实现并交付（改动 + 代码 + 实测 + 问题）
  → AI 按第 8 节评分 → 指导修改 → 总结错误
  → 通过后放行下一题 / 生成变体
```

### 生成新作业自检清单

- [ ] 是"需求"而非"API 演示"
- [ ] 指令类已按器件能力铺满
- [ ] 三段式齐全（功能 / 限定 / 验收）
- [ ] 白名单精确到函数名且不冗余，技术单列
- [ ] 圈定允许改动文件
- [ ] 验收含边界/异常/稳定性
- [ ] 引用的 API、引脚、器件真实存在
- [ ] 未泄露完整实现

## 11. 可直接复制的提示词模板

```text
请按「docs/practice_task_spec.md」标准，为「采集卡 FreeRTOS 练习」生成一份新作业。

- 需求：<一句话>
- 目标器件 / 数据结构：<INA228 / AT24C02 / W25Q128 / 缓冲区 / 状态机 …>
- 目标能力：<队列 / 互斥 / 定时器 / 纯代码能力 …，可留空>
- 难度：<L1 / L2 / L3>
- 前置作业：<A0 / 无>

要求：
1. 先阅读相关代码核实 API 名称与签名，再出题；
2. 只按三段式输出：功能 / 限定（只能改的文件 + 只能用(精确到函数名) + 技术）/ 验收；
3. 指令类给出精确的 指令→回复 格式（含 \r\n），并按器件能力铺满；
4. 不要给出实现代码；白名单外 API 需我先申请。
```
